## 2. R01：Worker 异常边界、毒消息与 ACK 一致性

**结论：属实，建议 P0。**

代码依据：

- `backend/src/agentplane/worker/main.py:279-302`：主循环只有 `try/finally`，没有消费异常隔离；`_reclaim_pending`、`xreadgroup` 和 `process_message` 的异常均可向外传播。
- `worker/main.py:148-202`：取 Run、标记开始、`_load_request` 和提交发生在运行时 `try/except` 之前。
- `worker/main.py:96-104`：查不到当前租户下的版本时抛出 `RUN_CONFIGURATION_MISSING`。
- `backend/src/agentplane/runs/service.py:238-243`：`attempt_count` 只在标记开始时递增，没有阈值判断；未发现死信处理实现。

持续前置异常的链路：QUEUED 消息被领取 → 标记 RUNNING 尚未提交 → 加载配置或历史失败 → 事务回滚 → Run 仍 QUEUED、计数也回滚 → 异常退出消费循环，未 ACK → 有其他消费者或外部重启后，消息达到 idle 阈值被重新领取 → 再次触发同一错误。当前部署只包含基础设施，项目自身没有实现 Worker 自动重启；因此“崩溃循环”以存在重启机制或其他 Worker 持续领取为前提。没有重启时表现为 Worker 停止服务。

边界：错误格式的 `aggregate_id` 已有日志和 ACK 分支；正常外键约束限制了版本被随意删除，因此配置缺失不是所有正常业务请求都能触发的错误。但持久的数据异常、加载失败以及数据库/Redis 异常缺少隔离的问题确实存在。

**同一检查发现另一条 P0 路径：** `worker/main.py:242-264` 在失败状态写入或提交再次抛错时，仍可能进入 `finally` 并成功 ACK。此时任务可能保留 RUNNING，消息却已不再 pending。不能只在主循环补 `except`，还必须修正 ACK 的执行条件。

改进方向：

1. 为完整消息处理过程建立异常边界；基础设施故障退避重连，单条永久错误隔离，取消信号单独处理。
2. 区分执行次数、投递次数和前置失败次数，计数必须能跨失败事务保存；不能直接复用会回滚的 `attempt_count`。
3. 永久错误可直接失败；可重试错误设上限和退避。不得将全局数据库不可用简单归类为每条消息的永久失败。
4. ACK 前必须确认终态或可恢复的失败处置记录已持久化。超限时保存失败原因与死信记录，再 ACK；跨 PostgreSQL/Redis 的死信投递需通过 Outbox 或等价机制保证可补偿、幂等。
5. 业务工具产生副作用后，自动重试必须受工具幂等策略约束。

验收：前置异常重复投递不会退出整个 Worker；健康任务继续执行；前置失败计数递增并按上限终结；终态提交失败不 ACK；重复投递和死信补发不重复执行业务写入；Redis/数据库恢复后服务能继续消费。

## 3. R02：停机取消可能留下已 ACK 的 RUNNING 任务

**结论：缺少完整优雅停机属实，原描述低估了风险。建议 P0。**

代码依据：`worker/main.py:213-264`、`279-323` 和 `backend/src/agentplane/asyncio_compat.py:10-19`。

项目没有“停止领新任务 → 限时等待在途任务 → 保存中断结果或保留恢复机会 → 关闭资源”的协议。入口使用 `asyncio.Runner`/`asyncio.run`，不能表述为 Python 完全没有任何中断处理；但项目没有自己的停机协调逻辑。

`asyncio.CancelledError` 直接继承 `BaseException`，不会被当前 `except Exception` 捕获，仍会进入 `finally`。一次任务取消不意味着后续所有清理 await 都立即失败，ACK 可能成功。相关语义见 [Python 3.13 任务取消文档](https://docs.python.org/3.13/library/asyncio-task.html#task-cancellation)。

必须区分两种结果：

- ACK 未完成：RUNNING 消息仍 pending，后续被 reclaim 时，现有分支将其标为 `WORKER_INTERRUPTED`。
- ACK 成功：Run 仍 RUNNING，但消息已从 PEL 移除，当前消费组不会再通过 reclaim 恢复该消息。`XACK` 的 PEL 语义见 [Redis 官方说明](https://redis.io/docs/latest/commands/xack/)。

改进方向：停止新领取，限时排空在途任务；超时后显式处理中断，先保存终态再 ACK，或保留 pending 供恢复。停机不等同于用户取消，应使用独立原因。关键收尾采用有时限的保护并重新传播取消；不能简单吞掉 `CancelledError`。增加数据库侧陈旧 RUNNING 对账，作为消息状态失配的补救。

验收：空闲、加载请求、模型等待、提交结果各阶段发起取消；补充目标操作系统的真实停机信号和强制退出测试；尤其验证“状态未落盘而 ACK 成功”不会发生，并区分可控停机和强制终止。

## 4. R03：消费者实例身份与所有权保护

**结论：部分属实。默认身份冲突需要修复，但同名不自动造成所有消息互相续期。**

`backend/src/agentplane/config.py:44` 默认 `worker-local-1`，未经配置覆盖的多个进程会共享 consumer 名，无法准确区分实例归属及监控指标。

不过，`worker/main.py:78-94` 的心跳明确传入 `message_ids=[message_id]`。XCLAIM 重置的是指定消息的 idle 时间，不是该 consumer 全部消息的统一租约。不同进程分别处理不同 ID 时，不会仅因同名而自动替对方续期。见 [Redis XCLAIM 语义](https://redis.io/docs/latest/commands/xclaim/)。

仍有需要单独治理的所有权风险：心跳使用 `min_idle_time=0`，未核对消息是否已被其他实例接管，也未检查 XCLAIM 返回值。即使消费者名称唯一，失去所有权的旧执行者也没有 fencing（执行代次校验）来阻止继续写事件、终态或执行工具。唯一命名是必要改进，不能代替执行所有权控制。

改进方向：默认生成“前缀 + 主机/实例标识 + 进程或随机后缀”，保留可配置前缀；设计所有权校验及执行代次；回收数量应与即时可执行容量匹配，避免一次 reclaim 10 条后串行处理、尚未开始的消息长期无心跳。

验收：多个实例身份唯一；不同消息独立续期；旧实例暂停超过回收阈值后恢复时不能覆盖新执行者状态；验证批量 reclaim 中等待执行的消息。建议 P1，多实例部署前完成；出现实际双执行或业务写工具时，应按 P0 处理所有权问题。

## 5. P01：SSE 已有唤醒，优化点是查询放大与重放边界

**结论：部分属实。“只是 sleep、没有真正唤醒”不属实；每轮三次查询与无界重放属实。**

代码依据：`backend/src/agentplane/api/event_stream.py:35-52`、`backend/src/agentplane/runs/service.py:203-219`。

本地已安装的 `redis/asyncio/client.py:1101-1114` 中，`get_message(timeout=...)` 等待消息或超时后返回；收到通知可提前结束等待并开始下一轮数据库读取。调用方不使用消息正文，并不意味着消息没有唤醒作用。目前是“通知唤醒 + 超时兜底 + 数据库读事实”，符合数据库保存权威事件的设计。

实际问题：

- 每轮 `list_run_events_after` 内部先查 Run 授权，再查事件；外层又查 Run 终态，合计三次查询。
- 空闲时默认约每秒兜底查询；通知密集时可能查询更频繁，积压通知还可能引起无效查询。
- 事件查询没有 `limit`，从起始游标重放会一次性加载所有剩余事件；10 万条是风险示例，本次未生成或压测该数据量。

改进方向：保留通知唤醒与数据库重放，合并同轮授权/状态查询、合并通知；事件按 sequence 游标分页，存在积压时连续读下一页，不为每页强制等待；空闲兜底可退避。不要为了减少查询直接取消必要的授权检查。Redis 断连重订阅与数据库兜底也需要明确处理。

验收：通知能在兜底超时前触发查询；丢通知仍可读取事件；大规模重放内存受页大小约束；跨页顺序与 Last-Event-ID 正确；终态事件全部发出后才关闭；比较空闲连接和高频通知下的查询量。

## 6. P02：流式事件逐条事务

**结论：属实，建议 P1；实际容量需压测。**

`worker/main.py:60-67` 对每条运行时事件打开会话、读取 Run、追加事件、提交并发布通知。`runs/service.py:180-199` 内部还要锁 Run、读取 `max(sequence)` 并插入事件；`runtime/langgraph.py:136-141` 将文本 chunk 转为 `model.delta`。取消检查也会额外查库。

当前行锁和 `(run_id, sequence)` 唯一约束是顺序保证的一部分，不能简单去掉锁。全局数据库 sequence 只提供分配序号，不自动保证同一 Run 的事务提交顺序；并发提交次序与游标读取不匹配时可能漏读较早分配、较晚提交的事件。

改进方向：优先按短时间窗口/字节数合并文本增量或批量写入，保留工具与状态事件语义；在 Run 行维护事件序号区间或使用等价的事务内分配方案。终态前必须冲刷已接受的缓冲事件，并明确缓冲期间崩溃的持久性取舍、背压与内存上限。

验收：重组文本与原结果一致；工具/状态事件顺序不变；终态前冲刷；取消及失败无缓冲泄漏；多连接重放不漏事件；测量事务数、数据库负载和首字/增量延迟的变化。

## 7. P03：数据保留与容量治理

**结论：自动清理与归档策略缺失属实，建议 P1。**

| 数据 | 代码现状 | 建议 |
|---|---|---|
| Redis Run Stream | `queue.py:55-63` 的 XADD 无 maxlen；生产源码未发现 XTRIM/XDEL，ACK 仅移除 pending 记录 | 按已处理安全边界裁剪，监控长度和最老待处理消息 |
| auth_sessions | `access/service.py:127-148` 登录新增、登出标记 revoked；鉴权检查过期时间，但未见定期过期清理 | 按 expires_at/revoked_at 分批清理并配置保留期 |
| run_events | 持续追加，无定期归档与保留策略 | 区分热重放、审计保留及归档数据；明确历史游标过期契约 |
| outbox_events | 已发布记录保留，无定期清理 | 只清理已发布且满足保留期的记录，保留失败诊断信息 |

边界：用户停用会删除其 AuthSession，删除父记录也可能通过外键级联清理相关数据，因此不能描述为“绝无删除路径”。问题是正常长期运行下缺少自动生命周期管理，并非本次已经确认线上存储耗尽。

不要直接添加固定 MAXLEN 就视为解决：裁剪必须保护尚未读取及 pending 的消息，并考虑所有消费组与故障恢复需要。保留期和容量阈值应由实际业务审计要求、吞吐与恢复窗口确定。

验收：活跃会话不误删；过期数据可分批清理；Stream 裁剪不丢待处理消息；事件归档不破坏约定的审计及重放能力；清理任务可重入并有容量指标。

2. **任务取消**：模型替身进入等待后调用执行 Task 的 `cancel()`；使用真实 `process_message` 的清理逻辑，随后查询持久化状态并统计 ACK 调用。

结果：


前置失败验证证明异常穿透主循环、事务回滚和未调用 ACK；配置缺失是人工注入，并未证明正常外键约束下可以删除被引用版本。取消验证证明该路径会在 RUNNING 状态调用 ACK；Redis 替身不证明真实网络下 ACK 必然成功，消息失去 reclaim 机会是结合 XACK 语义的推论。

本次未实测多 Worker Redis 竞争、SIGTERM/强制停机、数据库断连、SSE 延迟及 10 万事件重放。上述场景均已写入对应验收要求，不应将静态或替身证据标记为真实生产验证。

4. 并发、流式写入、上下文预算与重放性能根据试点负载推进；长期运行前完成数据保留策略。
5. Worker 异常隔离、ACK/终态一致性和停机误 ACK 修复作为近期可用性底线，在扩大真实试点前完成；持久化恢复、多实例和完整运维按对应部署需求推进。

## 11. 运行可靠性专项实施计划

计划状态：已规划，尚未实施。此节针对任务稳定处理、故障有明确结果、基础设施恢复后继续服务，批次编号仅适用于可靠性专项。业务功能顺序以第 10、12 节为准。可靠性第一批以现有单 Worker 部署为验收起点；多实例安全、自动重试和完整生产可用性需要后续批次共同完成。

### 11.1 第一批：修复已确认的 Worker 故障路径

目标：单条错误不会退出消费循环；没有持久化处理结果的有效任务不会被误 ACK；主动停机可限时收尾；已经写入的终态不会被旧执行路径覆盖。

| 工作项 | 计划改动 | 完成标准 |
|---|---|---|
| A1 完整异常边界 | 覆盖取消息、加载请求、执行、保存结果和 ACK；明确区分基础设施连接异常、单任务异常与取消 | 错误消息之后的正常消息仍可执行；Redis/数据库短暂不可用后恢复消费 |
| A2 ACK 条件 | 将 ACK 从无条件 finally 移到确认处理完成的分支；finally 仅做资源清理 | 终态提交失败不 ACK；终态成功但 ACK 失败，重复投递只补 ACK，不重跑模型 |
| A3 前置错误终结 | 配置缺失等确定性错误，以独立事务记录 FAILED 和错误事件；无法落库则保留 pending | 不再出现前置异常反复退出进程；失败原因可通过现有 Run 查询和 SSE 查看 |
| A4 可控停机 | Worker 接收停止事件；停止领取，限时等待在途任务；超时取消并记录中断，无法落库时保留 pending | 空闲和忙碌停机均可结束；取消路径不留下“RUNNING + 已 ACK”的新任务 |
| A5 终态保护 | 在持有 Run 行锁时检查状态和 dispatch_message_id，再写事件/结果；陈旧回调不得覆盖终态 | 已失败或取消的 Run 不会被晚到的成功结果改写；重复终态事件不重复插入 |
| A6 消费基础配置 | 每次进程启动生成唯一 consumer 身份；单任务执行时 reclaim 数量匹配容量，保留扫描游标并兼顾新消息 | 多进程名称可区分；不提前领取一批长期无人处理的 pending 消息；回收扫描不长期滞留同一前缀 |

第一批采用的失败策略：

| 场景 | 处理决策 |
|---|---|
| Redis/数据库连接类短暂故障 | 有上限的退避间隔和可取消等待；保留未完成消息，恢复后继续；不因全局故障批量判定任务永久失败 |
| 确定性的前置配置/数据错误 | 直接持久化失败，成功后 ACK；第一批不自动重试这类错误 |
| 未分类的单任务前置错误 | 记录异常并尝试持久化失败；保存失败则保留消息并退避。避免无限自动重试同一程序错误 |
| 已开始的模型/工具运行失败 | 延续现有失败终结策略；不新增整次 Run 自动重跑，保留现有模型 SDK 自身重试行为 |
| 执行中断或停机排空超时 | 已有用户取消请求时保留用户取消语义，否则记录 Worker 中断；保存失败则不 ACK |
| 数据库 commit 返回异常、结果不确定 | 用新事务查询实际状态；若终态已提交则只补 ACK，查明前不重跑也不覆盖结果 |
| 重复消息、Run 已终态 | 验证后 ACK，不执行模型，不再追加终态事件 |
| 消息格式错误或 Run 不存在 | 保留现有丢弃语义并记录结构化原因；第二批增加持久化隔离记录 |

推荐配置起点（仅为实施初值，需验证后调整）：基础设施退避 1 秒起、最大 30 秒并加随机抖动；停机排空 30 秒、收尾最多 10 秒；Redis 读写需有限超时，并与阻塞读取时间协调。服务管理器的终止宽限必须大于排空和收尾总预算。

信号处理放在 Worker 入口，核心 Worker 使用停止事件，便于单测。分别验证 Windows 控制台停止和 Linux SIGINT/SIGTERM；不把 task.cancel() 单测当作操作系统信号验收。强制终止无法保证收尾，此时依赖保留的 pending 消息；恢复策略仍是将已运行的任务明确标为中断，而非断点续跑。

第一批计划涉及：

- `backend/src/agentplane/worker/main.py`：异常边界、消费循环、条件 ACK、停止协调与心跳清理。
- `backend/src/agentplane/runs/service.py`：持锁校验、状态转移与幂等终态写入；核查全部调用方，避免影响用户取消和现有测试。
- `backend/src/agentplane/config.py`、`.env.example`：实例名称、退避、超时及停机预算配置。
- `backend/tests/`：新增 Worker 故障测试，扩展真实 PostgreSQL/Redis 集成用例。

第一批预计不新增业务表、不调整 HTTP 请求/响应结构；如实现需要额外内部模块，可在 worker 包内拆分。保持单 Run 执行方式、租户授权和 Session 活动任务约束。持久化失败计数、死信、执行代次及历史孤儿任务修复属于第二批，不能在第一批完成后将 R01/R03 整体标为完成。

### 11.2 第二批：让恢复过程可控、可追踪

目标：补齐 R01 的有界重试/死信与 R03 的所有权控制，处理历史或极端故障造成的状态失配。

1. 在数据库保存消息处理失败次数、下次尝试时间与最后错误，区别于现有 attempt_count。只有明确允许且尚未产生副作用的错误进入自动重试；基础设施整体中断单独退避。
2. 优先考虑数据库中的失败隔离记录作为首版 DLQ，与 Run 失败在同一事务保存；以 stream/group/message_id 等标识去重。无有效 Run 的坏消息也可记录，避免必须依赖合法 run_id。若另加 Redis DLQ，需补可靠投递流程。
3. 为执行引入 owner/执行代次与可验证的存活信息；事件、结果和心跳核对所有权，丢失所有权后停止旧执行路径。数据库写保护不等于外部业务工具恰好执行一次，写工具仍需独立幂等。
4. 为陈旧 RUNNING 建立对账：结合执行存活、消息状态和足够宽限判断，不能仅凭 created_at 或 updated_at 超时就判死。历史孤儿任务先只读列出，再按明确条件修复。
5. 本批包含增量迁移与默认值/索引设计；迁移、旧数据兼容、回滚及双 Worker 接管测试作为单独验收项。

### 11.3 第三批：调用结果可持续获取、服务状态可判断

1. SSE 保留“数据库事实 + Redis 唤醒”，Redis 订阅失败时有界退避并降级数据库读取；恢复后重订阅。按 sequence 分页重放并消除同轮重复 Run 查询。
2. 完善健康状态。当前 `api/system_routes.py:38-50` 在依赖异常时返回 degraded 内容，但未显式设置非成功 HTTP 状态；计划让 readiness 对依赖故障返回 503，保留 liveness 表示进程状态。另行呈现 Worker 存活和队列积压，避免将 API 健康等同于任务执行健康。
3. 制定并实现数据保留策略，先确定消费恢复边界、审计保留期和历史重放约定，再裁剪 Stream、清理过期会话及归档事件。
4. 高频事件批量持久化放在上述行为稳定后单独推进，以便明确缓冲丢失窗口、背压及延迟取舍。

### 11.4 第一批验收清单与执行边界

| 验收场景 | 预期结果 |
|---|---|
| 前置加载失败，随后投递健康任务 | 故障 Run 有明确失败结果，Worker 继续处理健康任务 |
| 保存失败结果时数据库异常 | 不 ACK；数据库恢复后可终结或重放已有终态 |
| 保存成功结果后 ACK 网络失败 | 不再次执行模型；重投递补 ACK |
| commit 结果不确定 | 重新读状态后决策，不重复执行，不覆盖已提交终态 |
| 执行 Task 被取消，数据库可用/不可用 | 分别保存中断结果后 ACK / 保留 pending，无误 ACK |
| 停机时队列空闲或模型正在等待 | 停止新领取；预算内收尾；资源关闭 |
| 停机与用户取消同时发生 | 用户取消语义和终态保持一致，终态事件唯一 |
| 旧执行者晚到的事件、成功结果 | 不改变已提交终态 |
| Redis 消费断连后恢复 | 退避期间无忙循环，恢复后可消费；等待期间仍可停止 |
| 重复消息和现有业务链路回归 | 租户隔离、幂等、事件顺序、SSE 重放、会话活动 Run 约束保持正确 |

验证分层：先用内存数据库/替身覆盖异常分支，再以专用测试租户和独立 Stream 验证真实事务、ACK、回收与重启；故障注入使用独立测试服务，不中断现有共享数据库或 Redis。运行仓库质量检查，并在具备独立服务的环境执行集成测试。第一批无需真实付费模型即可验证故障协议，完整模型/企业工具闭环另行验收。

发布前检查存量 pending 与 RUNNING：确认哪些仍有活跃执行者，列出已有状态失配；不把部署新代码视为自动修复旧任务。第一批完成标准是通过上述验收，不是仅通过静态检查或 Worker 能启动。

### 12.1 第一批：真实只读工具闭环

目标链路：管理员配置受控工具 → Agent 发布版本绑定工具 → 应用代表已映射用户调用 → 服务端验证有效权限及数据范围 → 查询真实业务系统 → 返回结果并可追踪本次工具调用。

| 内容 | 最小交付范围 | 验收重点 |
|---|---|---|
| 工具定义与版本 | 明确 tool_key、名称、说明、版本、输入/输出契约、风险级别及实现标识；工具实现先由服务端受控注册 | 未注册实现不能执行；参数不合法时稳定返回错误；已发布 Agent 能定位其使用的工具版本 |
| 工具管理 | 管理端可查看工具详情、版本、可用状态，并控制启停和授权 | 停用在执行入口生效；明确已排队任务和已开始工具调用的停用语义 |
| 可信执行上下文 | 服务端传递 tenant_id、user_id、可选 application_id、run_id、trace_id；延续应用/用户/Agent 工具权限交集 | 普通 Playground 无应用身份仍可按用户授权运行；应用调用不允许客户端伪造最终执行身份 |
| 统一工具执行入口 | 输入校验、权限与数据范围校验、超时、错误归一化及审计 | 租户或用户不能借工具参数扩大数据访问范围；下游错误能定位但不泄露凭据 |
| 一个真实业务查询工具 | 选择现有业务系统的受控只读 API；不先开放任意 HTTP、SQL 或脚本执行 | 从真实数据源返回可核对结果；无权限、无数据、超时三种情况行为明确 |
| 工具调用审计 | 保存调用标识、身份、工具版本、结果状态、耗时及脱敏摘要，并关联 Run | 能查清谁通过哪个应用调用什么工具；参数和结果中的敏感内容按规则处理 |

工具版本的持久化、Agent 绑定方式和审计表结构在下一步详细设计时确定；预期可能需要数据库迁移、API 与管理页面调整，应一并列出兼容与契约生成影响。本轮不将具体表名或接口路径作为已确定实现。

真实查询工具的实现依赖：目标业务系统及查询用途、现有 API/认证方式、用户允许查询的数据范围、可复用测试账号或样例。上述信息目前未确定，不擅自选定客户、订单、合同等业务对象；可以先完成平台侧契约与权限方案。

### 12.2 第二批：用量与模型记录准确

- 按每次模型调用汇总 Token，覆盖模型→工具→模型的多轮流程；流式统计去重，缺失用量标记为不可用而非默认为零。
- 固定本次 Run 使用的模型配置标识/版本与必要参数，记录实际执行模型，避免 API 和 Worker 配置不一致造成审计偏差；不保存明文密钥快照。
- 成功、失败和取消时尽可能保留已取得的用量；只有数据完整且有价格依据时才计算费用，区分估算与实计。
- 验收使用可控模型替身验证累计逻辑，再选择真实模型核对一次完整多轮调用。

### 12.3 后续批次及必要底线

写工具上线前，一起完成审批恢复、工具幂等、数据范围和执行记录；只读工具阶段不要求先建完整审批系统。

并发上限与配额、应用级锁优化、文本增量批处理、上下文 Token 预算、事件分页及归档按表中问题分别跟踪。达到上下文或容量限制时应提前安排对应项，不将所有中优先级工作无限延期。

可靠性底线沿用第 11 节的异常隔离、条件 ACK、终态保护与取消收尾；完整 DLQ、多实例接管和断点恢复按需求推进。任务恢复方案必须区分服务恢复、失败重试和业务断点续跑，不能将三者视为同一能力。
